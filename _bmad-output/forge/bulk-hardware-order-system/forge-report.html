Bulk Hardware Order System

Forge report · session goal: test whether the idea holds up · greenfield demo project · 13 questions

Outcome

Hardened. The idea holds up as a demo-scoped system. Enterprise clients place bulk hardware orders, prices come from ERP reference data, the system owns the order lifecycle, and clients can view history and cancel orders while it is still safe.

The test forced several changes to the original brief. "Net total" became payable total. A fuzzy "active request" became an explicit cancel rule. A single actor became three personas. "Bulk" turned out to be descriptive, not a pricing rule. The pitch that "this is a thin layer over an ERP" was not refuted. It was scoped out for the demo.

Locked decisions

LockPricing.
payable total = (Σ ERP MRP × qty, tax-inclusive) × (1 − client flat discount %), rounded once on the total, + shipping unless waived
  • No tax split. This system issues an order confirmation, not a tax invoice; billing stays in the ERP.
  • Price snapshot (MRP per line, discount %, shipping, payable total) is frozen when the order is created.
LockOwnership. This system owns the order record and lifecycle. The ERP mock is read-only reference data: catalog and MRP, flat discount, active-contract flag, per-order shipping quote, waiver flag. It has a "simulate unavailable" switch.
LockIntake.
  • Quantity is a whole number from 1 to 10,000 per line. An order has 1 to 100 lines. Every SKU exists in the ERP, there are no duplicate SKUs, and the client has an active contract.
  • Any failure, including ERP unavailable (retryable error), refuses the order and creates nothing.
  • One order is one destination and one shipment. There are no partial shipments.
LockLifecycle.
INTAKE → PROCESSING → SHIPPED → FINAL_DELIVERY
PROCESSING ⇄ BACKORDERED (whole order waits)
CANCELLED (client, only from INTAKE or BACKORDERED)
  • Cancel check and status write are atomic, so a client cancel cannot race a staff transition. No cancellation reason is captured.
LockPersonas (dropdown, no auth)
  • Enterprise User: picks a client from a seeded list, then places, views and cancels orders for that client only. Sees only its own discount.
  • Warehouse Operator: sees all clients, performs forward transitions and BACKORDERED, cannot cancel or edit.
  • Invoice Employee: read-only view of delivered orders with their price snapshot.
LockHistory. A paginated list of the client's orders in all states, newest first, no filters. Each order has an append-only, timestamped status timeline (transition, time, persona).

Rejected, and why

  • RejectedTiers, per-SKU rates, rebates. The contracts use one flat percentage.
  • RejectedAuthoring contracts here. Terms come from the ERP.
  • RejectedComputing shipping here, or a flat-fee config. The ERP quote is the only source.
  • RejectedMulti-address orders and partial shipments. They break the one-status, one-quote model.
  • RejectedSeparate CONFIRMED and REJECTED states. Refusing at intake is simpler.
  • RejectedCancelling in PROCESSING, or cancel-as-request. Too costly for a demo; picking has begun.
  • RejectedPer-user roles inside a client, real authentication, a "billed" flag for Invoice Employee.
  • RejectedSize-based pricing thresholds. "Bulk" is descriptive; the only size rule is the 100-line cap.

Weak points that survived

  • Open"Why not the ERP's own client portal?" Greg and Splinter raised it. It was scoped out for the demo, not answered.
  • OpenTax correctness is unchecked. Discounting a tax-inclusive price is fine for a confirmation, but nobody verified it against any tax rules, so the demo must not be presented as a tax document.
  • OpenReal ERP shape is unknown. A mock friendlier than the real ERP (effective dates, inconsistent rate formats) will cause rework.
  • AssumedThe shipping quote is frozen at intake. This was never confirmed.
  • AcceptedThe dropdown "identity" is not a security boundary. A client-isolation bug would be invisible in the demo.
  • AcceptedPROCESSING cannot be cancelled by the client. A client who double-submits and is too slow must call an account manager.
  • AcceptedThere is no inventory. BACKORDERED is a manual call, and the delivered-to-billed handoff has no owner in the demo.
  • AcceptedFINAL_DELIVERY only means "last status". The name is slightly misleading.
